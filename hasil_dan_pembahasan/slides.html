Autonomous Drone Optical Flow Navigation & Multi-Sensor Attitude Fusion

Implementation of Real-time Drift-free Odometry & Sensor Fusion for GPS-denied Flight Operations

Author: Project Team / Skripsi Researcher
Platform: Raspberry Pi + Picamera2 + GY-86 IMU + ArduPilot/MAVLink

Project Background & Motivation

Why do we need autonomous optical flow navigation?

  • GPS-Denied Environments: Indoor warehouses, tunnels, and dense urban canyons block GPS signals entirely.
  • State Estimation Needs: For autonomous stabilization (Loiter/Position Hold), a drone needs to know its velocity and translation in real-time.
  • Low-Cost Edge Computing: Utilizing lightweight sensors (GY-86 IMU, HMC5883L Compass, VL53L1X/MAVLink Altimeter) with a Raspberry Pi companion computer.
  • Dynamic Tilt Distortions: Drone rotations warp camera images, generating fake optical flow that must be isolated from physical translation.

Sensor Reading & Multithreading

To achieve steady, low-latency measurements without frame drops, the companion program uses python threads and thread-safe shared variables:

Threads

  • imu_reader Thread: Reads MPU6050, computes integrated gyro angles, runs the complementary filter, updates attitude at 50Hz.
  • compass_reader Thread: Polls HMC5883L, normalizes magnetic fields, and provides stable magnetic heading.
  • mavlink_reader Thread: Polls flight controller for altitude (distance sensor) and internal telemetry.

Locks & Synch

  • attitude_lock: Guards attitude roll, pitch, yaw, and gyro rate updates.
  • compass_lock: Syncs magnetometer heading and timestamps.
  • distance_lock: Protects altimeter distance updates.
  • Thread Safety: Uses Python standard `threading.Lock()` to prevent memory corruption.

Mathematical Model of Optical Flow

Optical flow measures the velocity of pixel brightness patterns moving across the image plane. For a downward-facing camera, pixel displacements $(\Delta u, \Delta v)$ are mapped to translational velocities using focal length $f$ and altitude $Z$:

V_x^{body} = \frac{\Delta x \cdot Z}{f \cdot \Delta t}, \quad V_y^{body} = -\frac{\Delta y \cdot Z}{f \cdot \Delta t}

Where:

  • $Z$: Altitude above the ground plane (provided by Lidar/Sonar distance sensor).
  • $f$: Focal length in pixels, calculated based on sensor width and FOV:
    $f = \frac{Width}{2 \cdot \tan(\frac{FOV}{2})}$
  • $\Delta x, \Delta y$: Compensated translation values in pixels.

The Attitude Drift Problem

The Gyroscope Pitfall

Gyroscopes measure angular rate ($\omega$). Calculating attitude requires integration:

\theta_t = \theta_{t-1} + \omega \cdot \Delta t

Standard low-cost MEMS gyroscopes suffer from **sensor bias and noise**. Over time, integrating these errors causes the attitude value to drift uncontrollably away from the true angle.

The Accelerometer Pitfall

Accelerometers measure gravity to find tilt angles, but they are highly corrupted by **high-frequency vibrations (noise)** and drone linear accelerations.

Fusion is mandatory!

Complementary Filter Theory

The Complementary Filter acts as a **High-Pass Filter** for the gyroscope (trusting its quick changes in the short term) and a **Low-Pass Filter** for the accelerometer/magnetometer (trusting its absolute reference value in the long term).

Angle_{fused} = \alpha \cdot (Angle_{prev} + Gyro_{rate} \cdot dt) + (1 - \alpha) \cdot Angle_{ref}

Here, $\alpha = 0.96$ is chosen in this project:

  • $96\%$ of the new angle comes from gyroscope integration (smooth, fast, vibration-resistant).
  • $4\%$ of the new angle comes from the absolute sensor reference (pulls the angle back to reality, eliminating accumulated drift).

Roll & Pitch Estimation Code

# sensor_readers.py - Attitude Update Loop (50 Hz)
roll_gyro_deg = attitude_state["roll_deg"] + (xgyro_dps * dt)
pitch_gyro_deg = attitude_state["pitch_deg"] + (ygyro_dps * dt)

# Apply Complementary Filter blending Gyro with Accelerometer
attitude_state["roll_deg"] = normalize_angle_deg(
    (COMPLEMENTARY_FILTER_ALPHA * roll_gyro_deg)
    + ((1.0 - COMPLEMENTARY_FILTER_ALPHA) * roll_accel_deg)
)
attitude_state["pitch_deg"] = normalize_angle_deg(
    (COMPLEMENTARY_FILTER_ALPHA * pitch_gyro_deg)
    + ((1.0 - COMPLEMENTARY_FILTER_ALPHA) * pitch_accel_deg)
)

The blending constant COMPLEMENTARY_FILTER_ALPHA is set to 0.96, providing the perfect balance between high-frequency response and long-term stability.

Yaw Estimation & Magnetometer Fusion

Yaw cannot be corrected by an accelerometer since gravity is parallel to the yaw rotation axis. The project fuses the Z-axis Gyroscope with the HMC5883L Magnetometer: 

# Compass Heading Fusion using blend_angle_deg to handle 0-360 transition safely
yaw_gyro_deg = attitude_state["yaw_deg"] + (zgyro_dps * dt)

if compass_heading_deg is not None and compass_age_s <= COMPASS_FRESHNESS_THRESHOLD_S:
    attitude_state["yaw_deg"] = blend_angle_deg(
        yaw_gyro_deg,
        compass_heading_deg,
        1.0 - COMPLEMENTARY_FILTER_ALPHA, # 0.04 weight for absolute compass heading
    )
else:
    # Fallback to pure gyro integration when magnetometer is unavailable
    attitude_state["yaw_deg"] = normalize_angle_deg(yaw_gyro_deg)

Gyroscope Calibration

Offset Calibration

Gyroscope offset bias is calculated at startup while the drone is completely stationary. The script averages 300 samples to establish the bias offsets. 

# Standalone calibration
gx_offset = sum_gx / num_samples
gy_offset = sum_gy / num_samples
gz_offset = sum_gz / num_samples
Filtering Output

Subtracting these offsets from raw measurements is necessary. Any uncalibrated static offset would result in a constant angular speed reading, causing the attitude integration to drift rapidly.

Tilt Compensation in Optical Flow

When the drone tilts (pitch or roll), the camera rotates. This rotation shifts the entire image frame, producing a displacement vector that mimics translation (horizontal flight velocity).

\Delta x_{compensated} = \Delta x_{raw} - (scale\_x \cdot \Delta Roll_{reticle})
\Delta y_{compensated} = \Delta y_{raw} - (scale\_y \cdot \Delta Pitch_{reticle})

We compute d_reticle_x and d_reticle_y as the change in the attitude angle scaled to pixel equivalents, and subtract this rotation-induced flow from raw tracked flow to isolate true vehicle velocities.

Calibration of Tilt Scale Factors

To ensure precise tilt subtraction, the scaling factors scale_x and scale_y (mapping degrees of rotation to pixel shifts) must be calibrated:

  • Dynamic Calibration Mode: Initiated by typing 'c' in the console.
  • Movement: The user tilts and rolls the drone back and forth without shifting its physical location.
  • Calculations: The system collects ratios of camera displacement over attitude reticle movement:
    scale\_x = \text{median}(\frac{tx}{d\_reticle\_x}), \quad scale\_y = \text{median}(\frac{ty}{d\_reticle\_y})
  • Saving: Results are persisted in tilt_calibration.json for immediate reuse.

Camera Offset Compensation

If the camera is not mounted at the drone's center of gravity (CoG), yaw rotations create a secondary translation. The script compensates for this using the camera's offset coordinates $(O_x, O_y)$ in cm: 

# Calculate rotational velocity correction (in meters/sec)
yaw_rate_rad = math.radians(zgyro_dps)
v_offset_x = -yaw_rate_rad * (camera_offset_y / 100.0)
v_offset_y = yaw_rate_rad * (camera_offset_x / 100.0)

# Subtract offsets from calculated physical body velocity
vx_mps_body_comp = vx_mps_body - v_offset_x
vy_mps_body_comp = vy_mps_body - v_offset_y

This prevents yaw rotations (spinning in place) from registering as horizontal movements.

Flow-to-Velocity Conversion

With compensated translations ($tx_{comp}, ty_{comp}$) and altitude in meters ($Z$), the raw velocities are computed, rotated to absolute frame using Yaw ($\Psi$), and then filtered via rate-limiters: 

# Body frame velocity calculation
vx_mps_body = ((tx_comp * altitude_m) / (focal_length_x_px * dt_s))
vy_mps_body = -((ty_comp * altitude_m) / (focal_length_y_px * dt_s))

# Rotate compensated velocities to absolute frame (East/North) using compass Yaw
yaw_rad = math.radians(-yaw_deg)
vx_mps_calc = vx_mps_body_comp * math.cos(yaw_rad) + vy_mps_body_comp * math.sin(yaw_rad)
vy_mps_calc = -vx_mps_body_comp * math.sin(yaw_rad) + vy_mps_body_comp * math.cos(yaw_rad)

# Apply acceleration rate-limiter (clamp to 15.0 m/s^2 max acceleration)
max_dv = 15.0 * dt_s
vx_mps = np.clip(vx_mps_calc, prev_vx - max_dv, prev_vx + max_dv)
vy_mps = np.clip(vy_mps_calc, prev_vy - max_dv, prev_vy + max_dv)

Position Tracking & Path Integration

Calculated velocities are integrated over time to track the drone's absolute position $(x, y)$ in centimeters: 

# Update physical position state
with position_lock:
    position_state["x_cm"] += vx_mps * dt_s * 100.0
    position_state["y_cm"] += vy_mps * dt_s * 100.0
    
    # Store trajectory path for plotting/visualization
    current_x = position_state["x_cm"]
    current_y = position_state["y_cm"]
    position_state["path"].append((current_x, current_y))

This enables real-time trajectory visualization, displaying the 2D top-down flight path on the dashboard.

Shared Memory Architecture (SHM)

To transfer high-frequency (60Hz) navigation state data across processes (e.g., from the tracker stream to the logger and web services) without pipe overhead, a Python SharedMemory buffer is implemented.

SHM Layout: [Magic Header (4 Bytes)] + [Write Index (4B)] + [Count (4B)] + [120 Samples x 88 Bytes Data]
  • Structure: The data package writes timestamp, position $(X, Y)$, raw position, velocities, altitude, and heading.
  • Performance: Zero serialization overhead, sub-millisecond reader/writer latency.
  • Unlink Safeguards: Uses shared memory locks and automatic resource tracker unregistration to avoid segmentation faults.

Experimental Setup & Methodology

Validation was performed using simulated and real flight logs logged in the hasil_dan_pembahasan directory:

  1. Setup: Drone was fixed to a test stand allowing rotations along three axes.
  2. Sensors: GY-86 MPU6050 + HMC5883L magnetometer logging raw and filtered angles.
  3. Data Logging: Ran `collect_sensor_data.py` to record pure integrated gyro, raw accelerometer/compass, and complementary filter outputs.
  4. Analysis: Executed `analyze_sensor_data.py` to compute Root-Mean-Square Error (RMSE) and Drift rates.

After Calibration

  • Residual noise is reduced to white noise with low standard deviation.
  • Calibration parameters are stored as static JSON files.

Conclusion & Future Work

Key Accomplishments
